# 连续对局维护说明

连续对局把固定两人的多场单挑归为一组。每场仍是独立比赛，复用正式计分、撤销和终场流程；组内胜场由比赛记录计算，不另存一份成绩，也不重复计入球员生涯。

## 使用与状态

赛前选择“单场比赛”或“连续对局”，默认单场。第一场确认开赛时才创建整组。组内双方固定，可使用临时姓名，也可交换红蓝方；不能用姓名、球员档案或红蓝颜色代替组内身份。

单场结束后可直接开下一场，或先修改规则、计时和红蓝位置。下一场从零开始，不继承分数、事件、计时进度和记录完整度确认。同一时间最多一组未结束对局、一场活动比赛；场间仍保留整组，首页可继续。

结束整组前必须先完成或明确放弃当前比赛。暂停和等待目标分／计时确认仍属于活动比赛，不能直接收局。结束后可从历史重新打开，但必须没有其他未结束组或活动比赛；重开不会自动创建下一场。

从单场赛果页结束整组后，保存成功才进入整组详情，展示全部场次并清除此前的连续开赛页面栈；返回进入历史。点击任意已完赛或已归档场次，可查看该场赛果和复盘，再逐级返回整组选择其他场次。取消或保存失败仍留在原页，失败可重试。

完赛及归档比赛参与胜场汇总，平局单列，放弃比赛不算胜负。纠分、删除比赛后重新计算，归档不改变成绩。没有完赛时不显示胜者或平局。永久删除单场仍遵守原有确认，关联随比赛删除，场次编号不复用；整组即使变空也保留，可结束或重新打开。

## 数据与事务

`match_series` 保存固定双方、状态、版本、递增场次号、最近成功开赛配置和生命周期操作意图；`series_matches` 保存每场所属整组、场次号和双方颜色对应。档案删除时清空引用，姓名快照继续保留。默认配置只保存规则、计时及颜色对应，不保存第二份姓名和档案引用。

开赛通过 `StartMatchCommand` 的可选整组上下文处理。创建／校验整组、比赛图、关联、活动比赛占用及回执同事务提交。普通单场省略新增上下文字段，保留旧命令 fingerprint。下一场使用预期版本和场次号；提交成功后重复请求返回原回执，过期请求不能跨结束、重开误建比赛。

整组结束与重开使用事务、预期版本及持久化意图，不能只依赖按钮禁用或内存标记。胜场从真实比赛派生；读模型应监听比赛事件及生命周期变化。

## 升级与备份

从 2.1.0 开始，数据库升级为 **schema 4**，JSON 外层格式仍为 **2**。schema 2／3 文件数据库自动迁移，既有比赛不会自动归组。2.0.1 安装包及其 schema 3 发行记录保持原样。

支持导入以下组合，按来源版本校验对应表组：

| JSON 格式 | 数据库 schema | 整组关系 |
| --- | --- | --- |
| 1 | 2 | 无，按旧规则导入 |
| 2 | 3 | 无，原比赛保持独立 |
| 2 | 4 | 包含整组及场次关联 |

**schema 4 备份需要新版 App 恢复，旧 App 无法导入。** CSV 和战报图片不能代替完整 JSON 备份。

替换恢复继续先保存并验证当前数据的安全备份，活动比赛期间不允许替换。合并导入不抢占本机活动状态：未结束整组转为已结束，原有未完成比赛按既有规则转为放弃；之后可在条件满足时重新打开整组。

合并时需成组处理 ID 冲突、档案引用、比赛子图、场次关系与命令回执引用／fingerprint，同一比赛不能误连两组。重复导入同一文件保持幂等。新增表纳入容量计数、校验和、完整图校验及自动备份变更标记，维持 32 MiB、单表 100,000 行、总计 200,000 行的共享上限。

## 验证入口

运行受影响的领域、备份、赛前及整组页面测试，再执行完整 Flutter 回归。Drift 结构变更需重新生成代码和 schema 快照；文案同步两份 ARB 并运行 `flutter gen-l10n`。

文件关闭重开只能证明文件恢复，不能代替 Android 进程冷启动。设备验证使用专用模拟器或隔离用户，覆盖活动比赛和场间恢复；集成测试后重建普通 Debug APK，再进行人工审阅。证据应注明基线与未提交改动摘要，不把开发构建称为正式发行。
