# HoopTrace 2.0.0 升级与备份 / Upgrade and backup

适用于 HoopTrace `2.0.0+4`。本版使用新正式签名，不能覆盖安装历史 v1；需要保留记录时，先从旧版导出完整 JSON 并确认文件已保存在应用之外，再卸载旧版、安装 v2 并恢复。维护者按无现有用户的情况豁免原证书设备覆盖升级，不记为通过。

新证书 SHA-256 为 `2820ba06e898be1152d38536492282127e9fb0734a0863bb42db63f8a75611dd`。正式 APK 的校验和、构建提交、CI 和设备范围见[发行记录](v2.0.0-release-record.md)，此前候选包保持各自历史来源。后续版本继续使用本次新证书，签名保护见[签名记录](v2.0.0-signing-upgrade-verification.md)。

## 中文：安装与数据保护

1. 从官方 Release 下载 APK，核对 SHA-256 和上述正式证书后安装。历史 v1 安装须先按上方步骤保护数据。
2. 有需要保留的记录时，在“设置 → 管理数据与备份”导出**完整 JSON**，保存到应用之外的目录或另一台设备。
3. 保留原文件，核对分享目标确实收到文件。JSON 包含球员、比赛事实、审计和命令 receipts；CSV 与复盘图片不能替代完整备份。
4. 历史 v1 APK 使用原证书，Android 会拒绝由本次新证书直接覆盖。旧包合成试验使用独立环境；卸载或清除数据不能被记录为数据保留升级，也不能由 Debug 结果证明正式同证升级通过。

当前正式包设备的实际范围见[发行记录](v2.0.0-release-record.md)。设备丢失、卸载或清除应用数据可能同时移除数据库和应用内安全副本，只有应用之外保存的备份能覆盖这些情况。当前豁免不改变下面的数据库与备份读取契约。

## 数据兼容契约

| 原有数据 | 2.0 行为 |
| --- | --- |
| 正式 v1.0 数据库 schema 2 | 保留既有增量迁移，增加派生分析快照表并升到 schema 3；合成文件库回归保留原来源，原证书设备覆盖本轮豁免，未记通过 |
| 已有 schema 3 数据库 | 直接打开，不升到 schema 4 |
| JSON 格式 1 / schema 2 | 接受、校验，分析快照从比赛事实重建 |
| JSON 格式 2 / schema 3 | 接受并校验事实、引用和快照；需要时从事实重建派生快照 |
| v0.1/schema 1 或不支持的格式组合 | 阻断并解释，不自动清空原库；保留原应用及已导出的资料 |
| 更新版本/更高 schema 的备份 | 拒绝，不降级写入现有库 |

旧比赛的 `scoresOnly` 不会因记录过未中或落点而自动变成“完整出手”。`shotAttempts`、`locations`、`full` 的历史声明仍保留。结束确认或明确修正才会更新记录范围；修正写入审计并保留幂等 receipt，不改写比赛事件。

## JSON 容量与失败行为

导出和导入使用相同的单载荷限制：

- UTF-8 JSON 最大 **32 MiB（33,554,432 字节）**；
- 单表最多 **100,000 行**；
- 所有备份表合计最多 **200,000 行**。

计数包含命令 receipts、审计和派生快照，不只是比赛事件。达到字节上限的时机取决于真实记录和每次命令投影大小；不能仅凭比赛场数估算。超限错误展示实际值与上限，导出在打开分享前失败，导入在改变数据前失败；原数据保留。保留原应用数据与已有外部备份，不通过删除历史或丢弃 receipts 来缩小备份。

长比赛回归实测 135 次真实命令，完整备份为 3,054,170 字节、398 行；这只说明该测试样本可往返恢复，不承诺任意比赛长度。[详细实测](v2.0.0-candidate.md#容量实测)。

## 替换、合并与内部安全副本

- **合并**将有效备份确定性加入本机数据，处理冲突 ID，保留本机偏好和本机活动比赛；不会让导入的活动会话占用本机活动位置。仍需符合既有合并校验规则。
- **替换**覆盖本机数据库前，先将当前状态保存为应用内安全副本。临时文件写入并 flush，回读后完整解码校验，再通过同目录原子 rename 发布。任一步失败都会阻断替换。
- 快照采集、文件保存和数据库替换保持同一个事务及 SQLite 非变更写预留，避免另一业务写入在“已备份”与“已替换”之间穿过。数据库替换失败会回滚。
- **回退**在数据页选择安全副本恢复，也会先保存当前状态。替换或回退都要求没有活动比赛；先完成或明确放弃当前比赛，再恢复。
- 数据页展示最近两份有效副本；成功替换后才进行保留清理。损坏、超限或临时文件不被当作可恢复副本，选中恢复时再次校验。
- 内部副本位于应用 documents 下的 `hooptrace-safety-backups`，在数据库之外，但仍属于应用私有数据。它保护替换误操作，不能代替外部 JSON。
- 替换或回退后自动备份授权/启用状态重置。需重新选择目录并明确开启；默认关闭，不自动沿用外部授权。

内部安全保存失败时检查设备存储并重试；损坏文件和不支持版本不要反复替换尝试。系统分享成功不代表文件已保存，更不代替内部安全校验。

## CSV 13 列契约

2.0 改变的是可读 CSV 的列契约，**JSON 格式仍为 2，数据库仍为 schema 3**。下游表格或脚本需按标题适配：

| 顺序 | 列名 | 含义 |
| --- | --- | --- |
| 1 | player_id | 关联档案 ID；临时参与者为空 |
| 2 | player_name | 档案昵称或当场名称快照 |
| 3 | match_id | 临时参与者所属比赛；档案汇总为空 |
| 4 | participant_id | 临时参与者 ID；档案汇总为空 |
| 5 | matches_played | 已结束/归档比赛数 |
| 6 | wins | 已结束/归档胜场 |
| 7 | points | 对应样本的已记录得分 |
| 8 | field_goal_made | 已记录投篮命中数，不含罚球 |
| 9 | field_goal_attempts | 已记录投篮出手数，不含罚球 |
| 10 | field_goal_percentage | 可信 FG%，0–100 数值、两位小数；否则空 |
| 11 | free_throw_made | 已记录罚球命中数 |
| 12 | free_throw_attempts | 已记录罚球出手数 |
| 13 | free_throw_percentage | 可信 FT%，0–100 数值、两位小数；否则空 |

球员统计只用已结束或归档比赛，档案按 ID 汇总；临时参与者只按单场参与者身份分行，同名不合并，也不因同名档案而被忽略。只要该汇总包含未声明完整出手的比赛，百分比保持空；各自分母为零也为空。事件 CSV 和比赛 CSV 仍保留原始导出范围，包括活动、放弃或删除标记，不能据此把这些样本当作生涯统计。

## English: installation and data protection

HoopTrace `2.0.0+4` uses a new production Android certificate, so it cannot update the historical v1 APK in place. Export a complete JSON backup from the old app, confirm that a readable copy exists outside the app, then uninstall v1, install v2, and restore. The original-certificate device upgrade was waived by the maintainer because there are no existing users; it is not marked as passed. The new certificate is listed above; APK hashes, build/CI commits and actual device checks are bound in the [release record](v2.0.0-release-record.md). Earlier packages retain their historical provenance.

1. Download the official Release APK and verify its SHA-256 and production certificate before installing. Preserve any historical v1 data with the steps above.
2. Export a **complete JSON backup** of any records you want to keep from Settings → Manage data and backups. Keep it outside the app, preferably on another device as well.
3. Keep the original file and verify that the selected target received it. CSV and replay images cannot restore players, audit history, or command receipts.
4. The historical v1 APK uses a different certificate, so Android rejects an in-place update with this package. Use an isolated environment for old-package experiments; uninstalling or clearing data does not prove a data-preserving upgrade, and Debug checks do not prove a formal same-certificate upgrade.

Future versions should retain this new certificate. Local DPAPI credential copies and their verified copies on C: and D: are not two offline backups, and are not directly portable to a different Windows account or computer. Signing evidence and the remaining offline-backup preparation are documented in the [signing record](v2.0.0-signing-upgrade-verification.md).

The candidate retains schema 3 and JSON format 2. Schema 2 databases retain the existing incremental migration; schema 3 databases open unchanged. Format 1/schema 2 and format 2/schema 3 backups are supported. Legacy schema 1, unsupported pairs, and newer schemas are rejected without silently erasing existing data. The current signing waiver does not alter these compatibility rules; historical synthetic migration checks retain their original source and do not establish a signed v1 device upgrade.

Coverage is a declaration, never inferred from misses or locations. Old scores-only matches keep that declaration. Explicit finish confirmation or a correction updates coverage with an audit and receipt.

## English: recovery boundaries

A single complete JSON backup is limited to **32 MiB of UTF-8**, **100,000 rows per table**, and **200,000 total rows**. Audit logs, receipts, and snapshots count. Export fails before sharing and import fails before mutation when a limit is exceeded; the error reports the measured size/count and limit. Keep the source data and existing backups rather than discarding history or receipts.

Replacement requires a private safety copy to be flushed, read back, validated, and atomically published. A SQLite write reservation covers snapshot capture through replacement; a failed transaction rolls back. Restoring a safety copy also protects the current state first. Both operations are blocked while a match is active. Successful recovery normally retains the latest two valid copies.

Safety copies live outside SQLite but inside the app's private documents directory. Uninstalling, clearing app data, or losing the device can remove both database and copies. They protect replacement mistakes and do not replace an external JSON backup. Automatic backup is reset after replacement/rollback and must be explicitly configured again.

Merge preserves local preferences and the active slot, remaps conflicting IDs, and follows existing validation. A system share action alone proves neither external file persistence nor safe recovery.

Player-statistics CSV now uses the **13 columns in the table above**. Profile IDs aggregate finished/archived games; temporary participants stay separate per match and participant. FG and FT use separate counts/denominators. Incomplete aggregate coverage or a zero denominator leaves the corresponding percentage cell empty. Raw match/event exports retain their broader record scope. JSON remains the recovery format.
