## 工具与隔离

使用 [observe_automatic_backup.py](../../tool/release/observe_automatic_backup.py)。工具本身只读设备；不启动应用、Worker 或接收器，不注入到期时间，不强制任务、不改时钟、不撤销授权、不提权。两种命令只执行一次，不创建定时任务。它要求显式设备 serial 和实际独立用户名称，默认 user 10，拒绝 user 0；输出必须在所有 Git checkout 之外，且不得覆盖旧证据。

每个 snapshot 保存实际 Android epoch、uptime、boot id、用户／UID、安装包路径与完整 APK SHA-256、应用 schema 3 数据库副本、全部自动备份设置、11 张业务表及非备份设置的逐行／rowid 指纹、唯一 WorkSpec、该 UID 的授权和 Worker 日志、目录文件及实际 JSON 字节。数据库 base/WAL 连续两次一致后才在主机副本中合并；最多尝试三次，不冻结设备进程、不对设备数据库 checkpoint。未完成快照保留 `INCOMPLETE.txt`，不可用于验收。

SAF 文件证据来自既有离线调试接收器 `io.github.x1a0y4ngren.hooptrace.acceptance_receiver`，源码和 APK 位于仓库外 `D:/DevCache/HoopTraceV2NativeAcceptance/`。操作其 **Inspect synthetic backup folder**，只选择当前应用授权的 `Documents/HoopTraceV2Synthetic…` 目录。接收器使用自己的只读持久授权查询文件并回读字节，不恢复 HoopTrace 已撤销的授权。snapshot 读取 `files/latest-proof.json` 和对应 `files/received/` 字节；目录 URI 必须完全一致，检查记录须在最近 300 秒内，数量、MIME、长度与 SHA-256 均需匹配。接收器的 20 文件／20 MiB 夹具上限不等于应用的 50 份保留／32 MiB 容量契约；本次选用小型合成数据，触及夹具上限须记录阻碍。

在 PowerShell 中先核实独立用户实际名称；下例的 `HoopTraceSynthetic` 必须替换为设备真实名称：

```powershell

& 'D:/Environment/Python313/python.exe' tool/release/observe_automatic_backup.py snapshot `
  --adb 'D:/Android/Sdk/platform-tools/adb.exe' --serial emulator-5554 --user 10 `

  --source-commit '<实际 APK 源码的 40 位 commit>' `

  --output 'D:/DevCache/HoopTraceV2Artifacts/backup-device-20261005/natural-before'
```

`source-commit` 是 APK 构建来源，不自动取当前文档 HEAD。工具读取设备安装的 `base.apk` 并验证预期 hash，还记录所有 split APK 的 hash。数据库、JSON、日志和证据不进入仓库，不访问真实球员资料。

## 自然等待

1. 在声明的合成用户下确认没有活动比赛。通过正常 UI 选择合成目录并启用自动备份，确认基线手动文件存在。若旧 unique work 曾用于强制／到期 fixture，先通过 UI 关闭并重新开启，使新任务来自正常调度；记录新 WorkSpec id。
2. 通过正常 UI 作一个普通修改，例如修改合成档案名称；不结束比赛，不注入 dirtySince。立即转到接收器刷新目录并采集 `natural-before`。确认 `enabled=true`、`dirty=true`、dirtySince 在快照前 300 秒内、唯一 WorkSpec 间隔 `86400000`、没有活动 session、HoopTrace 已在后台。
3. 从该快照起保留设备正常时钟与调度。期间不启动 HoopTrace、不结束比赛、不手动备份、不改业务数据／设置／授权、不替换 APK、不强制 job、不写应用或 WorkManager 到期元数据。模拟器不得 quick-boot／恢复快照；本工具对跨 boot 的自然时间证据保持 pending。记录任何意外操作，保留失败样本。
4. 满实际 24 小时后刷新接收器目录，运行同样的 snapshot 命令到新的 `natural-after`。这是观察下限，不是执行时刻保证：系统可延迟 WorkManager；dirtySince 的 24 小时门槛独立于 periodic work 的首次运行／周期时间，首次周期可能只返回成功而不写文件，需继续观察真实下一周期。
5. 用保存的快照比较；确认完整观察区间符合第 3 步后才能传 `--unforced-interval`。该参数是操作者的区间声明，两个离散快照不能独立证明期间从未操作。

```powershell
& 'D:/Environment/Python313/python.exe' tool/release/observe_automatic_backup.py verify `
  --mode natural --unforced-interval `
  --baseline 'D:/DevCache/HoopTraceV2Artifacts/backup-device-20261005/natural-before/snapshot.json' `
  --after 'D:/DevCache/HoopTraceV2Artifacts/backup-device-20261005/natural-after/snapshot.json' `
  --output 'D:/DevCache/HoopTraceV2Artifacts/backup-device-20261005/natural-observation.json'
```

退出 0 为通过，2 为 pending，1 为失败／无效证据。不足 24 小时或尚未看到文件时保存 pending，稍后用新目录重采；不回填通过。工具检查 Android epoch 与同一 boot 的 uptime 均满 86400 秒、两者差异不超过 10 秒，原唯一 WorkSpec 的 period_count 增长、state 回到 ENQUEUED 且 run_attempt_count 为 0，同时该 UID 的 epoch 日志包含对应 id 的 Worker SUCCESS。还要求 lastBackupAt 在 dirtySince+24h 后推进、dirty 清除且 dirtySince 删除、新 `hooptrace-auto-…json` 文件与 lastBackupPath 对应、合法 envelope/checksum／行数／容量、业务表和非备份设置完全不变。日志被覆盖则保留 pending，不能用 period_count 或目录时间单独补成通过。

Python 只验证 JSON envelope／checksum／计数及共享容量，**不能替代生产 `JsonBackupCodec.decodeAndValidate()` 的领域／图检查和真实 restore**。自然观察成功后还需在主机内存数据库验证新文件可恢复、再导出后 event／audit 的插入顺序和 receipt 保留。可参考仓库外既有 `D:/DevCache/HoopTraceV2Artifacts/3a0166c/verification/validate_native_backup_test.dart`，但替换旧文件路径与旧数据固定数量，不能直接把旧通过日志当作新文件结果。保留实际测试源、完整通过日志和 hash，创建仓库外 `restore-proof.json`：

```json
{
  "source_commit": "<实际 APK 的 40 位源码 commit>",
  "backup_sha256": "<natural-after 中新 JSON 完整字节 SHA-256>",
  "decode_and_validate": true,
  "restore": true,
  "round_trip": true,
  "test_source_path": "D:/DevCache/HoopTraceV2Artifacts/backup-device-20261005/validate_observed_backup_test.dart",
  "test_source_sha256": "<实际测试源 SHA-256>",
  "log_path": "D:/DevCache/HoopTraceV2Artifacts/backup-device-20261005/restore-test.log",
  "log_sha256": "<完整通过日志 SHA-256>"
}
```

仅在实际通过后填写上述布尔值。重新运行 verify，增加 `--restore-proof <路径>` 和一个新 `--output`。工具核对 source、精确 JSON hash、日志及测试源字节 hash；结果保存证据链。`natural_schedule_observed=true` 可与整体 `status=pending` 并存，此时只表示调度／写入已观察，生产恢复仍欠证据。
