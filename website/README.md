# Hoopito · 球豆 介绍与下载网站

**官网：[简体中文](https://hoopito.com/) · [English](https://hoopito.com/en/)**

网站与 Flutter App 位于同一仓库，独立构建。Astro 输出静态 HTML，TypeScript
管理交互，GSAP 驱动页面动效，Three.js 按条件加载连续球场场景。

中文首页 `/`、英文首页 `/en/`；网站隐私说明分别为 `/privacy/` 和 `/en/privacy/`。
两种语言共享组件，文案集中在 `src/data/content.ts`；语言切换保留当前章节锚点。
真实计分与复盘截图随语言切换，网站文案独立于 Flutter ARB。

导航按实际固定栏高度加 20px 对齐各章节的标题行，不把章节间的外层留白当作入口。
体验对齐球场输入舞台，复盘直达卡片落定与终场比分的阅读状态；刷新、语言切换、
浏览器前后退和尺寸重算使用同一定位方法，保留原生平滑滚动与 URL 锚点。
导航橙色细线按实际阅读章节切换，并通过 `aria-current="location"` 标注当前入口；
首屏和现场计分没有对应导航项，因此不亮线。手动滚动后不沿用旧 URL 锚点判断。
语言切换同样跟随实际阅读章节；“跳到正文”将键盘焦点交给正文，下一次 Tab 进入内容入口。

桌面投篮球场加载时显示由实际场景导出的 `scene-poster-demo-{compact,standard,wide}.webp` 俯视画面，
当前章节和宿主尺寸的首帧绘制完成后才显露 WebGL，避免先显示另一套二维球场。
该海报仅由桌面媒体条件请求，手机仍使用 SVG；WebGL 不可用、初始化超时或失败时
保留 SVG 操作降级。海报与既有开场占位一起导出、记录来源和校验，纳入桌面预算。

首页采用高对比运动海报构图，保留右侧近景篮球、连续球馆和薄液态玻璃材质。
首屏用真实 Black 字重大标题、独立说明和窄玻璃行动条；计分由真实横屏截图主导，
左栏将标题、说明和纵向功能选择合为完整阅读区，右栏保留大幅真实截图，两栏按实际内容对齐。
体验保留完整中央选点球场，记分牌与紧凑操作条分列上下。
复盘以真实赛果截图为主，紧凑走势、关键比分和历史档案为辅；下载将“球场见”标题
与包含版本、按钮和二维码的紧凑玻璃区分开。社区以大群号和邀请海报构成主次，
FAQ 使用开放问答行，与自然滚动的页尾共同收束。真实截图的 8:11、独立复盘示例
与网页演示 6:6 → 8:6 分别标注，截图内容、比例和真实像素保持不变。
复盘左栏的标题、说明与走势由静态 `replay-story` 网格依次排列，不用固定上边距叠放，
字体换行或文字放大后会自然撑开阅读高度，避免走势图遮挡说明。

桌面组件与镜头共享真实滚动位置、阅读边界和 `StoryFrame.cameraTrack` 转场进度，
不为组件建立第二个播放时钟。`data-story-item` 区分 heading、visual、control、detail，
`data-story-enter` 指定左右或纵向来源，`data-story-preset` 指定章节内的元素运动预设。
`story-choreography.ts` 根据同一轨道计算当前章退场与下一章入场：下一章主视觉在32–88%落位，
标题在50–94%揭示，操作区与说明在70–100%落稳。退场窗口为各自入场窗口的镜像，
操作区和说明先退，标题随后，主视觉最后让位，因此反向浏览也保持相同入场顺序。
复盘赛果、走势、历史分别使用32–84%、49–94%、66–98%的窗口。
明亮的计分与赛果截图使用更长的侧向退场距离，体验记分牌从上方收起，下载卡向上让出海报区域，
避免转场中两组图像或二维码叠在一起。空间预设仍是同一进度的纯函数，反向浏览准确还原。
镜头同步沿 `camera-track.ts` 与 `story-pose.ts` 的轨道移动。
反向滚动使用相同纯函数还原；阅读阶段组件静止，首屏直接可读，手机和减少动态效果直接落定。

标题与截图的揭示只作用于内层 `data-story-reveal` 容器；玻璃表面仅平移、统一缩放与透明度变化。
`data-glass-card` 只登记光学表面，与运动项分开；运动玻璃在同一元素上登记两者，禁止嵌套运动项。
同帧先更新组件，再读取玻璃轮廓和球场区域，最后提交场景状态；每章最多三个、相邻过渡最多
六个可见折射表面。计分、赛果和历史三个 App 截图容器只参与原有运动与大图查看，
不登记为玻璃；计分章只保留操作区、复盘章只保留分析区的光学表面。页面内容高于可用视口时保留完整自然阅读范围，
到达边界后由新手势切章；手机、无 JavaScript 与减少动态效果仍可阅读全部内容。
复盘图表在阅读区间呈现终场8:11；比分保持整行、不参与压缩，避免两位数换行引起舞台跳位。

已移除悬浮橙色装饰接力线及其定位／动画逻辑，避免它停留在标题、正文或卡片旁边。
右侧章节轨道、手机顶部阅读进度及按钮的功能选中标记保持独立。
所有舞台和独立组件均观察尺寸变化，静态网格高度决定固定资格；顶部导航实际高度写入
`--measured-header` 保护内容，基础 `--header` 不反向增大。尺寸变化继续暂停、重测并续播原切章目标。
原生 FAQ、校验及升级说明的 `toggle` 同样进入该刷新流程，覆盖浏览器延迟交付尺寸通知的情况；
关闭页面时移除监听。键盘／指针交互测试先观察真实锚点阅读落位，不用自动滚入仍在入场的组件替代导航。

章级组件分别负责构图，`poster-layout.css` 是章节布局与适配的唯一入口；
`immersive-glass.css` 管理场景和玻璃材质，`screenshot-viewer.css` 管理大图查看。
原有层叠的章节布局及翻卡样式已移除，下载弹窗和操作邀请仍使用各自的功能样式。
布局字体使用 rem，200%文字会真实增大并延长阅读范围。新增 `poster-story.spec.ts` 覆盖这些契约。

组件细节统一采用信息卡16px、操作条12px、按钮8px圆角；正文16px／1.7行高，
图注14px／1.6行高，导航至少14px。文字阅读保护只在文字区域使用一层可控遮光，
不在整张玻璃上叠第二层灰色面板；玻璃表面保留单层细边与轻阴影。
`.control-content` 仅承载按下时0.985的轻缩，`data-ui-icon` 承载最多2px的悬停反馈；
玻璃表面本身不添加悬停变换，避免光学轮廓与HTML脱节。FAQ答案使用内层淡入，
高度仍由自然内容决定；减少动态效果关闭这类反馈。截图版本与来源按独立文字单元排布，
窄卡片自然分行，图片内容和展示副本均保持不变。

## 本地开发与验证

使用 Node.js **24.x** 和 npm，在仓库根目录执行：

```powershell
Set-Location website
npm ci
npm run dev
```

开发地址为 [http://127.0.0.1:4321](http://127.0.0.1:4321)。其余命令均在 `website/` 执行：

| 命令                                       | 用途                                                                |
| ------------------------------------------ | ------------------------------------------------------------------- |
| `npm run check`                            | Astro 与 TypeScript 检查                                            |
| `npm run format:check`                     | 检查网站源码与文档格式                                              |
| `npm test`                                 | 演示、镜头衔接、画质滞回与响应式资源选择测试                        |
| `npm run build`                            | 生成 `dist/` 并检查页面实际资源图的压缩体积预算                     |
| `npm run preview`                          | 本地查看生产构建                                                    |
| `npm run test:e2e`                         | 在 Chromium、Firefox、WebKit 执行浏览器场景                         |
| `npm run assets`                           | 从仓库原始素材重新生成网页图片、字体、二维码和来源清单              |
| `npm run measure:perf`                     | 固定移动实验环境，冷缓存三次测量中英文 LCP、CLS 与真实请求预算      |
| `node scripts/measure-gpu.mjs`             | 独立有窗口 Chrome，分别记录环境、渲染提交与呈现证据状态             |
| `node scripts/check-journey.mjs --desktop` | 同一桌面会话检查中英文完整路径，保存截图、录像与 trace              |
| `node scripts/check-journey.mjs --android` | 在已有 Android AVD 的 Chrome 中检查中英文真实触摸路径               |
| `node scripts/export-scene-poster.mjs`     | 从当前生产构建导出桌面占位和移动同源背景，随后运行 `npm run assets` |

首次运行浏览器测试时安装对应浏览器，然后先构建：

```powershell
npx playwright install --no-shell chromium firefox webkit
npm run check
npm test
npm run build
npm run test:e2e
```

Playwright 自动启动本地 `preview` 服务；失败时保留 trace 与截图，报告位于
`output/playwright/`。CI 为每个任务仅安装所需浏览器；Linux UI 任务另装运行时依赖。
Playwright WebKit 在 macOS 原生 Cocoa 宿主运行，仍是其打包引擎的自动化覆盖，
不等同于实际 macOS／iOS Safari 验收。Linux WPE WebKit 的超时与布局／历史导航问题
仍由 [Issue #45](https://github.com/x1a0Y4NGren/hoopito/issues/45) 跟踪，不能据此声称 Linux 已修复。
构建预算以逐文件 gzip 计算：移动首屏每种语言不超过 500 KiB，桌面 3D
增量不超过 800 KiB。体积检查、模拟设备检查和真实 GPU 帧率各自保留证据。
CI 先执行 15 分钟有界的 `validate`，只构建一次；生成包含源码提交 SHA、逐文件
SHA-256、字节数和总摘要的 `build-artifact.json`，连同 `dist/` 上传当前运行的构建产物。
三个普通 UI 任务（Linux Chromium／Firefox、macOS WebKit，各35分钟、1 worker）与 Chromium
软件 WebGL 的两个分片（Windows，各35分钟、1 worker）只依赖 `validate`，使用独立 runner；
任一浏览器或分片失败不取消其余任务。普通 UI 关闭 WebGL，标记 `@webgl` 的检查按
[Playwright sharding](https://playwright.dev/docs/test-sharding)分到两个独立任务，分片内部串行运行。
两个分片的用例并集必须等于完整 WebGL 清单，均完成且零失败／flaky才算该组通过。
原生输入与逐帧计时使用单一浏览器 worker，避免同时绘制的另一用例干扰手势与命中测试。
三引擎的常规基线均为1440×900、DPR1；显式DPR1.5／2、缩放和高清缓冲用例另建上下文，保持原有密度与断言。
不沿用 Desktop Safari 预设隐含的DPR2来比较常规转场节奏，避免仅该引擎承担四倍像素的基线绘制。
任务总时限覆盖完整七章串行用例与诊断收集，单项断言、采样与产品初始化期限不放宽。
WebGL 任务使用 `playwright.webgl.config.ts`，保留完整 Chromium；CI 按
[Chromium 的软件 WebGL 模式](https://github.com/chromium/chromium/blob/156.0.8078.4/docs/gpu/swiftshader.md)
采用软件合成器，仅将 WebGL 绘制交给 SwiftShader，避免把它同时用作整个浏览器的 GL 驱动。
该配置继承原有用例、超时、画质与失败证据设置；本地仍使用现有真实 GPU 启动参数。
软件渲染检查只证明场景与交互生命周期，不代表真实 GPU 的显示帧率。
CI 的 WebGL 检查在 Windows runner 上以有窗口模式运行，直接使用其桌面，
通过 `npx playwright install --no-shell chromium` 安装完整浏览器，无需 Linux 的 Xvfb 或 APT。
共享 Linux 与 Windows runner 均出现过初始 WebGL 加载失败，由 [Issue #45](https://github.com/x1a0Y4NGren/hoopito/issues/45)
保留证据；切换执行环境本身不代表已修复，也不减少用例或放宽门禁。普通 UI 保持无头运行，本地启动参数不变。日志保存实际浏览器
启动参数，WebGL 报告附上现有画布、渲染器、可见性及运行环境信息。
WebGL 任务还保存 `runtime.jsonl`；Windows 仅记录平台、CPU 型号／数量等运行环境元数据
与子进程退出结果，不提供 Linux `/proc`、cgroup 或 Chromium 进程资源计数。
在 Linux 手动运行该采样器时，才以两秒间隔记录主机 CPU／内存、可用的 cgroup
资源限制与本任务 Chromium 子进程的原始计数，供失败时区分资源争用和进程积累。
采样不保存原始环境变量或命令行，不改变测试结果、时限、画质及绘制流程。
测试任务只下载当前工作流运行中按完整提交 SHA 命名的构建，校验本地源码身份、文件集合
及每个文件的 SHA-256 后才启动 preview，不重新构建或引用其他提交的“最新产物”。
失败允许一次诊断重试，但 `--fail-on-flaky-tests` 会将重试后通过也判为不稳定失败。
追踪保留失败时的动作、源码及独立失败截图，关闭持续截图与 DOM 快照采集。
原生滚轮序列逐包确认浏览器实际收到后再发送下一包，仍校验原有增量、数量与间隔。
持续追踪会在输入传输中产生额外往返，并对软件 WebGL 增加画面回读负担，不能与
真实输入／帧采样同时作为无干扰的计时依据；自有逐帧和输入回执继续保留。
各任务无论成功与否均保存独立 HTML／JSON 结果、执行状态、日志、trace 和失败截图，
按浏览器、WebGL分片及工作流运行次数区分，保留14天；构建身份摘要也随报告保存。
网站的 8 秒初始化回退期限与现有单测、断言超时保持原值。
密集俯视采样按有重叠边界的区间拆分，每种视口仍覆盖全部 63 个位置及相邻边的
双向检查，保留 2px／0.5° 精度。开场使用加载前安装的受控时钟和逐帧 `runFor()`
检查真实开场进度、中间／最终投影有效性与停绘；稳定阅读、下载和恢复交互使用真实时钟。
截图姿态与光学轮廓组按原飞行路径拆分，在受控时钟下每50ms采样一次真实生产绘制，
保留各截图的多个中间变换、六表面上限与0.1px轮廓精度；普通过渡录屏仍使用实际时钟。
普通录屏保留1440×900页面与原渲染密度，输出720×450审阅副本，避免共享runner的VP9编码积压拖住关闭；
下载／结尾静态截图仍按原视口保存，录屏容器帧率不作为GPU呈现性能证据。
录屏只包含真实相邻正反转场，完成后等待上下文关闭与视频保存；下载与结尾的1440×900截图及运行状态
由独立无录屏上下文校验，避免静态导航和截图也进入编码队列，90秒测试期限保持。

### 本地 GPU 与完整路径复验

使用当前 `dist/`，同一时刻只运行一组 GPU 测量、浏览器测试或 Android 模拟器验证。
GPU 测量期间保持 Chrome 窗口真实可见且拥有焦点，桌面路径退出后再运行 Android。
这些工具只需本地构建和浏览器／设备，不依赖部署或远端预览。

```powershell
node scripts/measure-gpu.mjs
# 完成后，在另一个终端保持 npm run preview 运行，再依次执行：
$env:HOOPITO_HEADED = '1'
node scripts/check-journey.mjs --desktop
node scripts/check-journey.mjs --android
```

GPU 脚本自行在本地随机端口提供 `dist/`，Windows 下默认测 AMD／NVIDIA × 1440×900／1920×1080
× DPR 1／2。每次配置使用独立 Chrome 进程和临时 profile：`cold` 是首个文档；
`warmed` 是同一 context 完成首轮工作负载后的第二个文档，保留进程／着色器缓存，
服务器仍使用 `no-store`。冷、热样本分别记录；独立进程的 trace 只用于诊断。

| GPU 环境变量                                       | 用途                                                       |
| -------------------------------------------------- | ---------------------------------------------------------- |
| `HOOPITO_GPU`                                      | 逗号分隔的适配器，默认 `amd,nvidia`；每次只读枚举实际 LUID |
| `HOOPITO_GPU_VIEWPORTS`                            | JSON 数组，例如 `[{"width":1440,"height":900,"dpr":1}]`    |

`experience-entry,replay-entry,reverse-story` 保留为历史锚点／脚本滚动诊断阶段，须显式选择。
`reading-drift` 在首屏静止阅读12秒，单独记录24次/秒上限下的 `readingCadence`；
其 `submissionGate` 为 `not-applicable`，不应用活跃操作的平均58次/秒与p95 20ms门槛。

查看 `measurements.json` 的 `environmental`、`submissionGate`、`presentationGate`，
分别判断环境资格、活跃渲染提交节奏和可归属于网站新内容的呈现证据。

呈现状态保持 `unavailable`，总体不能标为通过。合成器诊断回调、事件数量或时间邻近

## 场景与交互

大图查看有加载、失败与重试状态，失败或加载时暂停缩放；迟到的图片请求不会覆盖随后打开的图片。
窗口变化保留当前倍率，适应窗口按钮恢复 100%；支持拖拽、双指与 `+`／`−`、`0`、方向键操作。
短横屏优先保留图片和操作栏，完整操作提示仍由对话框的无障碍说明提供。
辅助说明使用至少 12px，手机辅助文案、安装与备份说明至少 14px；触控入口至少 48px。
文字放大时比分节点和演示按钮自然换行，已播放的聚光浮层不继续占据过期尺寸。

正文、截图和下载入口先由 HTML 呈现，所有章节呈现仍读取真实文档滚动位置。视口至少 1024px、
精细指针且支持 WebGL2 时，才加载单一室内球馆场景。桌面以篮球近景开场，
背景铺满视口，贯穿首屏、计分、体验、复盘、下载、社区与页尾。页面内容高于
可用视口时自然流动。767px及以下使用三张同源竖版球馆背景，首屏篮球近景、
计分至复盘的斜向球场、下载至结尾的篮架场边分别对应
`art/scene-mobile-{hero,court,hoop}.webp`。手机不请求 Three.js、桌面材质，操作演示保留SVG。
首屏只请求篮球背景，后续背景在首次实际滑动后按距离预取；直接锚点优先加载对应画面，
加载失败时保留上一张可用背景。背景交叉淡化和最多±6px视差使用现有滚动更新帧，
减少动态效果时直接切换并关闭视差。768px及以上的原有粗指针降级继续使用
`art/scene-mobile.webp`，桌面加载占位也来自同一场景。

`main.ts` 的 `gsap.matchMedia()` 管理响应式时间线和撤销。DOM 与场景共享
`StoryFrame { chapter, progress, active }`；`story-pose.ts` 让相邻章节复用端点，
同时插值镜头位置、朝向、视角和灯光。调整几何、灯光、材质或镜头后，先构建、
导出占位，再生成素材并重新构建；`assets/art/scene-poster.json` 绑定实际源码的UTF-8／LF规范化SHA-256与编译场景哈希。
导出器只观察当前页面创建的唯一渲染器；捕获时临时清空光学卡片并恢复，保存纯球场。
三张手机背景从2560×1600视口的实际桌面hero、scoring与download阅读镜头裁取9:16窗口，
横向中心分别为74%、50%、50%，按比例输出720×1280、WebP质量76，每张上限120KiB。
原有单图降级仍从1440×900的hero镜头裁取横向中心74%的窗口，最大768px宽、WebP质量68。
来源记录保留原始尺寸、裁剪矩形、镜头状态与输出哈希；检查篮球、球场纵深和篮架构图后再交付。
可设置 `HOOPITO_POSTER_OUTPUT` 将新增捕获记录与导出前记录保存在D盘；缺省使用
`output/court-continuity/`。旧捕获和旧记录保留，不覆写历史证据。

手机呈现样式集中在 `mobile-layout.css`、`mobile-motion.css` 和 `mobile-navigation.css`，
新规则仅作用于767px及以下。`mobile-presentation.ts` 复用 `main.ts` 的滚动更新帧，
按组件自身的静态位置计算入场，不移动体验章的记分牌、球场与操作区。
原生章节弹窗沿用下载与大图的暂停所有权；历史截图和二维码复用原有内容，
手机默认折叠，宽屏完整展开，旋转后保留手机端的展开选择。无JavaScript时保留原生目录与完整内容。

767px及以下、支持触摸且未开启减少动态效果时，手机启用章节边界吸附。
短章节至少占满导航下方的可用高度，长章节在自己的完整阅读范围内使用原生滑动；
当前手势到达边界后停住，结束后再用一次向外滑动切换相邻章节，不跳过脚注或展开内容。
边界手势移动超过8px且纵向达到横向的1.25倍后才接管；净滑动达到24 CSS px时，
松手从当前预览位置以1200ms余弦缓动切章，不足24px则以280ms回到阅读位。
预览行程最多为12vh与相邻停靠距离18%的较小值；一次手势最多一章，新触摸可接管旧动画。
`mobile-touch.ts` 只识别触摸意图，通过 `chapter-scroll.ts` 的内部触摸所有权接口
`beginTouch / moveTouch / endTouch` 复用滚动写入、惯性隔离、取消和重排续播，
不增加独立动画时钟或CSS滚动吸附。原生阅读的结束由 `scrollend` 与120ms静默兜底判断。
横向、多指缩放、文字选择、编辑控件、内部可滚动区和系统边缘手势保留原有操作。

手机导航最上缘的3px橙色进度线表示实际整页阅读进度，菜单同时显示两位章节页号。
`mobile-progress.ts` 在同一更新帧中计算进度；章内页号稳定，跨章阅读边界中点时切换。
进度线不接受点击，七章跳转仍由原生章节菜单提供；导航按实际高度测量并适配安全区域和大字体。
减少动态效果时关闭自动吸附，保留进度与即时菜单跳转；初始化失败或无JavaScript时自然滚动。

桌面各章节完整放得下导航空间时，固定舞台并增加1.15倍视口高度（115vh）的滚动距离，
按22%入场、56%阅读、22%退场分配卡片节奏。内容过高、窄屏或减少动态效果时自然排版；
镜头跨度按章节的实际边界计算，避免放大文字时提前切入下一段。
`ScrollTrigger` 提供原生滚动进度，卡片、镜头与章节状态共用该进度；同轮更新通过
microtask合并DOM变换和玻璃边界测量，再调用 `CourtScene.flushFrame()` 在同一帧提交场景。
`scene-commit.ts` 按镜头、玻璃、章节与视口的完整值去重同状态提交，不舍入亚像素；
同一帧内真正发生变化的轮廓仍立即提交。投篮、漂移和画质调整继续由场景自身驱动。
手机标题、操作和说明最多平移12px，主视觉最多20px并轻缩放，配合有限视差；
按钮和导航反馈为120–180ms。响应式时间线退出时恢复样式。

桌面精细指针且正常动效时，`chapter-scroll.ts` 统一接管章节边界的滚轮／触控板手势。
输入按CSS像素累计净方向，24px提交相邻章节；不足阈值停止140ms后以280ms回弹。
预览最多12vh或相邻停靠距离18%，切章1200ms；从当前实际滚动位置到相邻阅读边界，
使用 `(1 - cos(πt)) / 2` 平滑推进，不再采用旧pin入场／退场节点压缩阶段时间。
重排保留已确定目标、剩余时长及原曲线阶段；坐标变化时使用有界单调续段，
尽量承接已有速度，终点速度归零。距离骤缩时优先保证位置有界；已经位于目标阅读范围则直接完成。
镜头、DOM和光学轮廓继续消费同一真实滚动位置，不增加独立播放时钟。
转场期间输入全部消耗，不排队切章。落位后输入静止180ms即释放尾流；持续滚动无需先停顿：
至少三个同方向、每次≥24px且滚量不衰减的落位后输入，持续≥180ms后视作新的主动意图，
从当前阅读点再切相邻一章。高频小增量另按时间积分：落位后连续三个80ms完整窗口，
每窗同方向累计≥24px，末窗保留首窗至少90%的滚量，且不能连续两窗下降，即可确认新意图。
窗口总量吸收分包和舍入波动，不再要求每个小样本达到24px或逐个增大；确认当次消耗已累计的24px
直接切章，不要求额外补滚。衰减、短暂平台和低速小尾流继续拦截；方向反转、重排、取消和参与接管的
横向样本会清空候选。积分分支的活动门槛为24px／80ms，低于它的持续细小输入仍等待180ms静默释放；
此规则识别持续意图，不依赖鼠标移动，不声称能完美区分所有主动输入与惯性。
`StopId`在六个`StoryChapter`
之外增加仅用于导航的`closing`；FAQ移到社区之后，与原页尾共用最后停留页和社区末段镜头。
语言切换保留`#closing`。长内容按实际`readStart/readEnd`自然阅读，在边界拦住同一手势的剩余输入，
下一次新手势才切章。最后一页向下自然到文档末端。手机、减少动态效果、横向滚动、缩放、输入框
及可继续滚动的内部区域不受接管；点击导航、键盘、拖动、缩放、弹窗和后台会取消旧滚动任务。
`animation-clock.ts` 让前台 GSAP 动画按实际经过时间前进，避免软件绘制的连续长帧被压缩为33ms，
